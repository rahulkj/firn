firn vs. the field

Written by the project; as objective as we could make it. Treat every "firn wins" row as a claim to verify, not a conclusion. Competitor figures are vendor/community claims; firn's are measured.

Read this first. firn is a young, single-maintainer, zero-external-production-hours broker (~350–500 durable msg/s default). Kafka, Redpanda, Pulsar, RabbitMQ, NATS, Kinesis, Pub/Sub and SQS are million-hours-in-production systems. If you need a broker to run the business by, use one of those. firn wins in narrow, real places — see below.

TL;DR verdict

Firn is not superior as a general-purpose production broker. It is meaningfully differentiated in a few places:

  1. Stream + queue semantics on one append-only log with broker-native DLQ and one replication/audit path — the cleanest "task queue and event log in one system" among OSS brokers.
  2. Byte-offset-preserving passive federation with a fenced cutover — a DR story no mainstream broker ships out of the box (preview-quality, unproven at scale).
  3. Secure-by-default in the binary — bootstrap token, hashed keys, roles, per-key + per-IP rate limits, mesh mTLS, append-only audit always on. OSS Kafka/Pulsar/RabbitMQ/NATS make you assemble this (or buy a paid tier).
  4. MIT, ~12k LOC, single binary — the learning / embedded / teaching / edge niche.

In every boring axis — throughput, exactly-once, ecosystem, maturity, multi-tenancy, geo — firn loses, mostly by a lot.

Where you'd actually pick firn

  • Internal control-plane / service-mesh plumbing: a few hundred durable msg/s is plenty; you want it MIT and auditable.
  • Internal job dispatch where a DLQ + audit + least-privilege keys beats raw throughput.
  • An educational or reference implementation of "how brokers work".
  • A DR/standby pilot where byte-identical restore has real value and preview semantics are tolerable.
  • Embedded/edge: a ~14 MB static Go binary beats Erlang/JVM toolchains.

When to pick something else

  • AWS/GCP-native → SQS/Kinesis/Pub/Sub. Max throughput / Kafka API → Redpanda or Kafka. Multi-tenant platform → Pulsar. Enterprise task queue → RabbitMQ. Lightweight edge → NATS. Exactly-once → Kafka with transactions. Already on Redis → Redis Streams.

What would change this verdict

  • Group-commit flush windows at scale (ADR-014 shipped behind a flag; adoption evidence needed) → throughput column re-opens.
  • Cluster GA at scale + dynamic membership, rolling upgrades → Kafka-class HA story.
  • Kafka wire-protocol shim or first-class Schema Registry → ecosystem addressable.
  • One external production deployment with published numbers → maturity column stops reading "zero".
